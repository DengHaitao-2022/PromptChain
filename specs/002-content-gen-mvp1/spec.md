# Feature Specification: Prompt Chain 内容生成系统 MVP1

**Feature Branch**: `002-content-gen-mvp1`
**Created**: 2026-03-07
**Status**: Draft
**Input**: User description: "需求规格说明书（初稿 mvp1）：面向基于 Prompt Chain 的自动化内容生成系统"

## Overview

本规格用于定义一个面向开源项目以及产品化的内容生成系统 MVP。系统要把复杂内容创作从单次输入转换为可追踪、可暂停、可恢复、可回放的链式流程，并在关键风险点引入人工确认，提升过程可控性和结果可信度。

MVP 范围聚焦五项核心能力：用户登录与角色权限、工作流可视化编排、一键生成长文或脚本、不确定点检测与 Gate 门控、任务监控与结果回放。规格强调业务闭环、可演示性和文档完整性，不追求超出毕业设计所需的大规模商业化能力。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 普通用户发起并完成内容生成任务 (Priority: P1)

普通用户登录后，选择一个已发布工作流，填写主题、体裁、长度、风格和约束等输入项，系统自动完成意图卡、提纲、正文、自检修订等阶段，并向用户交付可查看的终稿与全过程产物。

**Why this priority**: 这是系统的核心业务价值，也是整个 MVP 是否成立的最直接判断标准。

**Independent Test**: 使用一个已发布工作流发起单次任务，验证用户能够从填写参数到查看终稿独立完成全流程，并看到所有关键阶段产物。

**Acceptance Scenarios**:

1. **Given** 普通用户已登录且存在可运行的已发布工作流，**When** 用户填写必填输入并提交任务，**Then** 系统创建任务实例并进入执行状态
2. **Given** 任务按标准链路执行，**When** 每个阶段完成，**Then** 用户可以查看对应阶段的中间产物
3. **Given** 任务执行成功，**When** 用户打开任务详情，**Then** 用户可以查看终稿以及形成终稿所依赖的关键过程信息

---

### User Story 2 - 用户处理 Gate 并继续执行任务 (Priority: P1)

当系统发现缺失信息、约束冲突或事实风险时，会暂停任务并生成关键问题。用户查看问题、补充回答后，任务从中断位置继续执行，而不是从头重跑。

**Why this priority**: Gate 是该系统区别于普通内容生成工具的关键能力，直接决定流程是否可控、可解释、可干预。

**Independent Test**: 发起一个会触发 Gate 的任务，验证系统能暂停、提出 1 至 3 个问题，并在用户回答后继续执行到终态。

**Acceptance Scenarios**:

1. **Given** 任务执行中存在缺信息、约束冲突或事实风险，**When** 系统完成当前检查，**Then** 任务进入等待确认状态且不再自动继续
2. **Given** 任务已进入等待确认状态，**When** 用户打开待处理事项，**Then** 用户可以看到与当前风险直接相关的 1 至 3 个问题
3. **Given** 用户已提交 Gate 回答，**When** 系统接收并保存回答，**Then** 任务从中断节点继续执行，且新的回答会影响后续结果

---

### User Story 3 - 工作流设计者创建并发布内容生成流程 (Priority: P2)

工作流设计者通过可视化方式创建或编辑工作流，配置节点、连线和节点规则，保存为草稿，并在通过合法性校验后发布给普通用户使用。

**Why this priority**: 该能力决定系统是否具备可维护、可扩展的流程配置能力，但不阻塞核心生成闭环的最小可演示价值。

**Independent Test**: 由设计者独立完成一次工作流创建、保存、校验和发布，并验证普通用户只能看到发布版本。

**Acceptance Scenarios**:

1. **Given** 设计者已登录，**When** 新建工作流并在画布中添加节点与连线，**Then** 系统保存流程结构和节点配置
2. **Given** 工作流仍为草稿，**When** 设计者重新打开该工作流，**Then** 系统恢复上次保存的流程内容
3. **Given** 工作流缺少关键节点或存在孤立节点，**When** 设计者尝试发布，**Then** 系统拒绝发布并指出不合法项

---

### User Story 4 - 用户或管理员监控并回放任务过程 (Priority: P2)

任务运行期间，用户或管理员可以查看当前状态、当前节点和历史节点记录；任务结束后，可以按照时间顺序回放节点输入、输出、异常和人工干预记录。

**Why this priority**: 监控与回放既服务演示和论文评测，也直接支撑问题定位、结果解释和人工复盘。

**Independent Test**: 打开一个已完成任务和一个运行中任务，分别验证实时状态查看、暂停恢复和回放时间线展示是否完整。

**Acceptance Scenarios**:

1. **Given** 任务正在运行，**When** 用户进入任务详情，**Then** 用户可以看到当前状态、当前节点和已执行节点记录
2. **Given** 任务允许被人工控制，**When** 用户执行暂停或恢复操作，**Then** 系统更新任务状态并保留上下文连续性
3. **Given** 任务已结束，**When** 用户打开回放视图，**Then** 系统按执行顺序展示节点输入、节点输出、异常记录和人工处理记录

---

### User Story 5 - 管理员维护账号与访问边界 (Priority: P3)

管理员负责维护用户账号状态、角色分配以及全局查看权限，确保普通用户只能访问自己的任务和被授权的工作流，设计者只能维护自己负责的工作流。

**Why this priority**: 它支撑系统安全与管理完整性，但在 MVP 中优先级低于内容生成闭环和 Gate 能力。

**Independent Test**: 通过三类角色分别登录，验证菜单差异、可访问对象范围和管理员管理动作是否符合权限边界。

**Acceptance Scenarios**:

1. **Given** 管理员已登录，**When** 新增用户或调整角色，**Then** 新权限在下一次登录或刷新授权后生效
2. **Given** 普通用户尝试访问其他用户的私有任务，**When** 系统校验访问权限，**Then** 系统拒绝访问
3. **Given** 设计者尝试编辑未授权工作流，**When** 系统校验维护权限，**Then** 系统拒绝编辑并保留原有工作流状态

### Edge Cases

- 当用户提交任务时缺少必填输入，系统如何阻止启动并指出缺失项
- 当工作流存在循环、孤立节点或缺失关键配置时，系统如何阻止保存或发布
- 当任务在等待 Gate 期间长时间无人处理时，系统如何保持等待状态并避免误继续
- 当任务暂停后恢复，系统如何确保不会重复生成已经确认的阶段产物
- 当结构化输出无法被后续步骤使用时，系统如何记录失败并阻止错误结果继续传递
- 当任务执行失败后被回放，系统如何同时展示已完成节点和失败节点信息
- 当管理员禁用账号时，系统如何处理该账号当前已登录会话和待处理任务

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须支持用户通过账号和密码登录，并建立受控会话
- **FR-002**: 系统必须在登录后识别用户角色，并按角色展示对应菜单、页面和操作权限
- **FR-003**: 系统必须支持用户主动退出，并在退出后阻止继续访问受控页面
- **FR-004**: 系统必须支持管理员新增、启用、禁用、查询用户，并为用户分配角色
- **FR-005**: 系统必须限制普通用户仅查看被授权工作流和本人任务，限制设计者仅维护本人或被授权的工作流，并允许管理员进行全局查看与管理
- **FR-006**: 系统必须允许工作流设计者创建新的工作流草稿，并填写名称与说明
- **FR-007**: 系统必须提供可视化流程画布，支持添加节点、连接节点、删除节点、移动节点位置和编辑节点属性
- **FR-008**: 系统必须至少支持开始、输入、生成、解析、条件、Gate、输出七类节点，以便配置标准内容生成链路
- **FR-009**: 系统必须支持工作流草稿保存，并允许设计者在后续重新打开继续编辑
- **FR-010**: 系统必须在保存或发布前校验流程合法性，至少覆盖开始节点缺失、结束节点缺失、孤立节点和关键配置缺失
- **FR-011**: 系统必须支持将通过校验的工作流发布为可运行版本，并确保普通用户只能选择已发布版本发起任务
- **FR-012**: 系统必须支持普通用户基于已发布工作流填写结构化输入并创建任务实例
- **FR-013**: 系统必须在任务开始阶段生成意图卡，用于明确主题、受众、体裁、风格、长度、约束和禁止项
- **FR-014**: 系统必须基于意图卡生成可用于后续写作的提纲，至少包含结构层级和关键要点
- **FR-015**: 系统必须基于提纲生成正文或脚本草稿，并保持与提纲结构的可对应关系
- **FR-016**: 系统必须在正文生成后执行自检修订，识别结构偏差、内容重复、表达问题和约束未满足情况，并产出修订结果
- **FR-017**: 系统必须保存意图卡、提纲、草稿、自检结果和终稿等中间产物，并允许在任务详情中逐项查看
- **FR-018**: 系统必须支持将上一步输出转化为可被下一步直接使用的结构化结果；若转化失败，系统必须记录异常并按任务状态处理
- **FR-019**: 系统必须在关键节点检测缺信息、约束冲突和事实风险三类不确定点
- **FR-020**: 当检测到不确定点时，系统必须触发 Gate 中断，将任务置为等待确认状态，并停止继续执行下游节点
- **FR-021**: Gate 必须向用户提出 1 至 3 个与当前不确定点直接相关的关键问题
- **FR-022**: 系统必须提供待处理 Gate/审批列表和详情视图，允许用户或管理员查看问题并提交回答
- **FR-023**: 用户提交 Gate 回答后，系统必须将回答写入任务上下文，并从中断位置恢复后续执行
- **FR-024**: 系统必须维护任务状态，至少包括待启动、运行中、等待确认、已暂停、已成功、已失败
- **FR-025**: 系统必须支持任务启动、暂停和恢复，并保证恢复后沿用原任务上下文而不是创建新任务
- **FR-026**: 系统必须展示任务当前执行节点、各节点执行状态和关键时间信息
- **FR-027**: 系统必须支持按时间顺序回放任务全过程，至少包含节点输入、节点输出、中间产物、异常信息和人工干预记录
- **FR-028**: 系统必须支持顺序执行与条件分支执行，以满足标准链路和 Gate 场景之外的流程扩展
- **FR-029**: 系统必须在任务运行过程中持续保存会话状态，以支持暂停恢复、Gate 继续执行和结果回放

### Non-Functional Requirements

- **NFR-001**: 系统必须通过浏览器即可访问，普通用户无需额外培训即可完成任务创建、结果查看和 Gate 处理
- **NFR-002**: 已发布工作流必须具备版本独立性，后续编辑草稿不得改变已发布版本对应任务的可追溯结果
- **NFR-003**: 当任务被暂停、等待确认或执行失败时，系统必须保留此前已确认的上下文和中间产物，不得要求用户重复输入已提供信息
- **NFR-004**: 系统必须保证每个任务的执行过程可追溯，可用于问题定位、演示复盘和测试评测
- **NFR-005**: 系统必须有效隔离角色权限，避免普通用户或设计者越权访问管理员功能或非授权资源
- **NFR-006**: 系统必须允许在不破坏既有工作流定义的前提下，后续扩展新的节点类型、模板规则和检测策略
- **NFR-007**: 系统范围必须控制在毕业设计 MVP 所需闭环内，优先保证核心流程可演示、关键证据可留存、结果可回放

### Key Entities *(include if feature involves data)*

- **User（用户）**: 系统中的身份主体，包含账号标识、角色、状态和审计信息
- **Role（角色）**: 权限边界的定义单元，用于区分普通用户、工作流设计者和管理员
- **Workflow（工作流）**: 一条可被维护和发布的 Prompt Chain 业务流程，包含名称、说明、归属和当前状态
- **Workflow Version（工作流版本）**: 工作流在某个时间点可运行的固定版本，用于区分草稿与发布态
- **Node（节点）**: 工作流中的单个处理步骤，描述步骤类型、名称、规则和在画布中的位置
- **Edge（连线）**: 节点之间的流转关系，描述顺序连接或条件分支
- **Task Run（任务实例）**: 用户针对某个工作流版本发起的一次实际执行记录
- **Session State（会话状态）**: 任务执行时持续累积的上下文信息，用于恢复、继续和回放
- **Artifact（中间产物）**: 任务在不同阶段形成的阶段性结果，如意图卡、提纲、草稿、自检结果和终稿
- **Gate Record（Gate 记录）**: 一次人工门控事件的完整记录，包含触发原因、关键问题、用户回答和处理状态
- **Execution Log（执行日志）**: 节点级运行证据，记录节点输入、节点输出、状态、耗时和异常

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在验收演示中，普通用户可在 3 分钟内完成一次任务发起，且无需借助管理员协助
- **SC-002**: 在标准样例任务中，至少 90% 的任务可在 10 分钟内到达终态；若任务包含人工等待，等待时间不计入该指标
- **SC-003**: 在触发不确定点的验收样例中，100% 的任务会在进入下游节点前被 Gate 正确拦截，并生成 1 至 3 个相关问题
- **SC-004**: 在 Gate 验收样例中，至少 90% 的任务能够在用户回答后从中断位置继续执行，而无需重新创建任务
- **SC-005**: 在任务详情或回放验收中，100% 的已完成任务都能展示意图卡、提纲、草稿、自检结果和终稿
- **SC-006**: 在权限验收测试中，100% 的越权访问尝试都会被拒绝，且不会暴露非授权任务或管理功能
- **SC-007**: 在工作流发布验收中，100% 的非法流程配置都会在发布前被拦截，并向设计者说明原因
- **SC-008**: 在回放验收中，100% 的已完成或已失败任务都能按时间顺序展示节点执行记录、异常信息和人工干预记录

## Assumptions & Dependencies

- 本规格面向毕业设计 MVP，默认优先满足“可运行、可演示、可回放、可写入论文”的目标
- 初始角色固定为普通用户、工作流设计者、管理员三类；更细粒度角色划分不属于本期范围
- 任务执行依赖系统已具备稳定的内容生成能力来源；该来源的供应方式不在本规格约束范围内
- 工作流运行以“已发布版本”为准，草稿仅用于编辑，不直接面向普通用户
- Gate 的处理者默认为任务发起者或管理员，不额外引入独立审核角色

## Out of Scope

- 面向大规模商业化场景的租户管理、计费、运营分析和复杂组织协作能力
- 与本期核心链路无直接关系的批量任务编排、跨项目知识库治理和高级内容分发能力
- 超出长文与脚本生成场景之外的多模态生产能力
