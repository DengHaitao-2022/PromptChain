# Feature Specification: PromptChain 统一错误体系

**Feature Branch**: `005-unified-error-system`
**Created**: 2026-04-11
**Status**: Draft
**Input**: User description: "MVP1 没有形成完整、统一的错误体系设计。现在更像是局部雏形 + 多套风格并存，可以支撑功能开发，但还不适合当成对外稳定契约。需要把统一错误模型、错误码注册表、异常分层、全局异常映射、基础设施异常脱敏和前后端契约统一记入 MVP2。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 前端和调用方获得稳定可判定的错误响应 (Priority: P1)

前端页面、控制台模块或其他 API 调用方在请求失败时，可以基于统一的错误响应结构和稳定错误标识做分支处理，而不是依赖中文文案或不同路由各自返回的临时格式。

**Why this priority**: 这是错误体系最直接的业务价值。只要调用方仍依赖自由文本判断错误，系统就无法形成稳定契约，也会持续放大前后端耦合和回归风险。

**Independent Test**: 选择多个不同领域的失败场景发起请求，若调用方能够基于统一错误结构识别错误类别并做出稳定处理，而无需解析自由文本，则该故事独立成立。

**Acceptance Scenarios**:

1. **Given** 用户请求因参数错误、权限不足或资源不存在而失败，**When** 调用方收到响应，**Then** 响应使用统一错误结构并包含可稳定判定的错误标识
2. **Given** 两个不同模块触发同一类业务失败，**When** 调用方处理响应，**Then** 调用方可以用一致方式识别该错误而不依赖路由差异
3. **Given** 调用方需要展示用户可理解的提示，**When** 请求失败，**Then** 响应同时提供对机器可判定和对人可理解的错误信息

---

### User Story 2 - 后端对领域错误与基础设施错误做一致映射 (Priority: P1)

后端在处理认证、权限、工作流、追踪、工作空间和外部依赖异常时，能够把不同来源的异常统一映射为一致的外部契约，并对基础设施故障做安全脱敏，避免直接把内部异常细节暴露给前端。

**Why this priority**: 没有统一映射，错误处理就会继续分散在各个路由和服务层，难以维护，也无法保证安全边界和日志追踪质量。

**Independent Test**: 在业务错误、权限错误和外部依赖错误三类失败场景下检查返回结果，若它们都能被统一分类、正确脱敏并保留可追踪线索，则该故事独立成立。

**Acceptance Scenarios**:

1. **Given** 某次请求触发了明确的业务规则失败，**When** 后端处理该异常，**Then** 外部响应映射为对应的业务错误而不是通用内部错误
2. **Given** 某次请求因数据库、模型服务、邮件服务或其他外部依赖异常失败，**When** 后端返回响应，**Then** 外部响应不会泄露底层实现细节，但仍保留可追踪的错误上下文
3. **Given** 不同路由触发相同类别的异常，**When** 系统返回错误响应，**Then** 对外语义保持一致而不是由各路由各自决定

---

### User Story 3 - 团队维护统一错误码注册表和复用规则 (Priority: P2)

后端开发者、前端开发者和后续维护者可以基于统一的错误码注册表和分域规则扩展新能力，不需要每增加一个功能就重新约定一套错误表达方式。

**Why this priority**: 统一错误体系不仅是运行时能力，也是团队协作契约。没有注册表和分域规则，系统会很快重新退化成多套风格并存。

**Independent Test**: 为一个新业务域补充错误定义并被前后端一致消费，如果整个过程不需要临时发明新格式或重新解释旧规则，则该故事独立成立。

**Acceptance Scenarios**:

1. **Given** 系统新增一个业务域或接口组，**When** 团队为该域定义错误，**Then** 新错误可纳入统一注册表并遵循既有分域规则
2. **Given** 前端需要处理一个新的业务错误，**When** 查看错误契约，**Then** 可以通过稳定标识与说明判断其处理方式
3. **Given** 团队复盘历史错误，**When** 查看错误定义和运行记录，**Then** 可以区分业务错误、权限错误和基础设施错误的边界

### Edge Cases

- 如果多个业务域出现语义相近但处理方式不同的失败，系统如何保证错误标识不冲突且不误导调用方
- 如果基础设施异常在短时间内频繁出现，系统如何在不暴露底层细节的前提下保留足够的追踪线索
- 如果旧接口尚未迁移到统一错误体系，系统如何在过渡阶段避免调用方误判
- 如果同一请求同时存在业务问题和基础设施问题，系统如何确定对外暴露的主错误语义
- 如果人工可读提示需要调整文案，系统如何保证机器可判定标识不受影响

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须为失败响应提供统一的外部表达结构，使不同接口在失败时遵循同一契约
- **FR-002**: 系统必须为错误提供稳定、可机器判定的错误标识，并允许调用方基于该标识而非自由文本做分支处理
- **FR-003**: 系统必须同时提供用户可理解的错误说明，使前端可以直接展示或映射为一致提示
- **FR-004**: 系统必须为每次失败响应提供可用于日志追踪和问题定位的请求关联标识
- **FR-005**: 系统必须建立统一的错误码注册表或错误标识清单，并按业务域划分稳定命名空间
- **FR-006**: 系统必须区分至少三类错误：业务规则错误、应用流程错误、基础设施依赖错误
- **FR-007**: 系统必须对认证、权限、工作流运行、工作空间、追踪与运维依赖等核心领域采用一致的错误映射规则
- **FR-008**: 系统必须通过统一入口将内部异常映射为外部错误契约，而不是由每个路由自行拼装错误格式
- **FR-009**: 系统必须确保数据库、缓存、模型服务、邮件服务等基础设施异常对外脱敏，不得直接透传底层异常文本
- **FR-010**: 系统必须允许前端和其他调用方区分“需要用户修正输入”“需要重新登录或申请权限”“需要稍后重试或联系管理员”这三类处理方向
- **FR-011**: 系统必须为过渡期的旧接口提供迁移策略，使统一错误契约能够逐步覆盖现有模块，而不是只在新接口中局部生效
- **FR-012**: 系统必须保证相同错误语义在不同接口中的外部表达一致，避免出现多个模块各自定义相近但不兼容的错误表示

### Key Entities *(include if feature involves data)*

- **Error Contract（错误契约）**: 对外暴露的统一错误表达，包含稳定错误标识、可读说明、追踪关联信息和必要上下文
- **Error Code Registry（错误码注册表）**: 用于归档不同业务域错误标识及其语义边界的统一清单
- **Error Domain（错误域）**: 用于区分认证、权限、工作流、工作空间、追踪和基础设施等不同错误来源的分类单元
- **Exception Mapping Rule（异常映射规则）**: 将内部异常来源转换为对外契约的统一规则
- **Error Event（错误事件）**: 一次请求或运行过程中被记录和追踪的失败事件，可关联请求、模块和最终外部响应

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 至少 90% 的失败接口能够返回统一错误结构，而不是使用各模块自定义的临时格式
- **SC-002**: 前端在处理核心失败场景时，至少 80% 的分支逻辑可以基于稳定错误标识完成，而不再依赖中文 `detail` 文案判断
- **SC-003**: 在认证、权限、工作流和追踪四类典型失败场景中，团队可以在 5 分钟内通过错误响应和请求关联标识定位到对应问题来源
- **SC-004**: 基础设施依赖故障对外暴露的原始底层异常文本数量降为零
- **SC-005**: 新增一个业务域时，团队能够在不发明新错误格式的前提下完成错误定义接入，并在一个迭代周期内被前后端共同采用

## Assumptions

- MVP1 已经具备多个 API 域和运行态场景，足以暴露统一错误体系缺失带来的真实成本
- MVP2 首先需要建立稳定外部契约，再逐步把现有局部风格迁移到统一体系
- 前端与后端都需要消费这套错误契约，因此错误体系必须同时兼顾用户提示、程序分支和日志追踪
- 统一错误体系优先服务于现有核心 API，不要求一次性覆盖所有历史内部工具接口

## Dependencies

- 当前主要 API 域的失败场景需要被盘点并归类，才能形成可用的错误码注册表
- 需要有统一的请求追踪标识或可挂接的请求上下文，才能支撑错误定位闭环
- 需要明确各业务域的权限边界和状态语义，才能避免错误码语义重叠

## Out of Scope

- 重构全部业务逻辑或一次性替换整个服务层架构
- 将所有历史内部脚本、测试桩或临时管理接口立即纳入统一错误体系
- 构建大型运维平台、告警系统或独立审计产品
- 通过统一错误体系直接解决所有业务状态设计问题
