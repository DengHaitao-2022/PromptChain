# Feature Specification: 基于 Prompt Chain 的自动化内容生成系统 MVP1

**Feature Branch**: `001-content-gen-mvp1`
**Created**: 2026-03-07
**Status**: Draft
**Input**: User description: "基于 Prompt Chain 的自动化内容生成系统 MVP1 需求规格说明书"

## Overview

本系统面向长文、脚本等复杂内容生成场景，解决单次 Prompt 在多步骤生成中容易出现结构不稳定、内容跑偏和事实错误的问题。系统通过"意图卡—提纲—写作—自检修订"的流程化方式，将复杂任务拆分为多个可执行步骤，并支持在关键步骤由用户确认后继续，以提升生成过程的可控性与可靠性。

### 术语定义

- **Prompt Chain**: 将复杂内容生成任务拆分为多个顺序或分支节点，通过节点之间的数据传递完成整体生成流程
- **意图卡**: 对用户需求进行结构化整理的中间产物，通常包含主题、受众、体裁、风格、长度和约束
- **Gate**: 当系统检测到缺信息、冲突或事实风险时触发的人工确认节点
- **中间产物**: 意图卡、提纲、草稿、自检报告等任务执行过程中的阶段性结果
- **任务实例**: 用户对某个工作流的一次实际运行记录
- **结果回放**: 按执行时间顺序查看任务各节点输入、输出、异常和用户干预情况的能力

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 普通用户一键生成长文 (Priority: P1)

普通用户登录系统后，选择已发布的内容生成工作流，填写主题、体裁、长度等输入参数，系统自动执行"意图卡—提纲—写作—自检修订"流程，最终输出终稿。

**Why this priority**: 这是系统的核心价值主张，直接体现"将复杂生成任务从单轮提示转化为链式流程"的能力，是 MVP 必须验证的关键功能。

**Independent Test**: 可通过单独运行一个包含完整链路的工作流，验证从用户输入到终稿输出的完整流程，无需依赖 Gate 或工作流编排功能。

**Acceptance Scenarios**:

1. **Given** 用户已登录且存在已发布的内容生成工作流, **When** 用户选择工作流并填写输入参数后提交, **Then** 系统创建任务实例并开始自动执行
2. **Given** 任务运行中, **When** 每个节点执行完成, **Then** 系统保存该节点的中间产物（意图卡/提纲/草稿/自检报告）
3. **Given** 自检修订节点完成, **When** 任务成功结束, **Then** 用户可查看包含意图卡、提纲、自检报告和终稿的完整产物

---

### User Story 2 - Gate 不确定点检测与人机门控 (Priority: P1)

在任务执行过程中，当系统检测到缺信息、约束冲突或事实风险时，自动触发 Gate 中断，向用户提出 1-3 个关键问题，用户回答后系统继续执行。

**Why this priority**: Gate 机制是系统区别于传统 AI 生成工具的核心差异点，体现"人机协作"和"风险可控"的设计理念，与 P1 的一键生成同等重要。

**Independent Test**: 可通过配置一个包含 Gate 节点的工作流，提供需要澄清的模糊输入，验证系统正确触发 Gate、呈现问题并在回答后继续。

**Acceptance Scenarios**:

1. **Given** 任务正在执行, **When** 系统检测到缺信息/冲突/事实风险, **Then** 任务状态变为"等待确认"并生成 1-3 个关键问题
2. **Given** 任务处于等待确认状态, **When** 用户查看并提交回答, **Then** 系统将回答写入任务上下文并从中断处继续执行
3. **Given** Gate 被触发, **When** 用户查看问题, **Then** 问题数量在 1-3 个之间且内容与当前不确定点相关

---

### User Story 3 - 用户登录与角色权限控制 (Priority: P2)

不同角色（普通用户、工作流设计者、管理员）登录系统后，系统根据角色加载不同的菜单和操作权限，确保权限隔离和安全访问。

**Why this priority**: 登录和权限是系统可用性的基础，但可以在核心生成流程验证完成后再细化，MVP 阶段可采用简化的角色实现。

**Independent Test**: 可通过分别以三种角色登录验证其可见菜单和可执行操作的差异。

**Acceptance Scenarios**:

1. **Given** 用户输入正确的账号密码, **When** 提交登录, **Then** 系统建立会话并跳转到对应角色的首页
2. **Given** 普通用户已登录, **When** 查看菜单, **Then** 只能看到任务创建、我的任务、Gate 处理等入口
3. **Given** 管理员已登录, **When** 查看菜单, **Then** 可看到用户管理、角色管理、全量任务等管理功能

---

### User Story 4 - 工作流可视化编排 (Priority: P2)

工作流设计者通过可视化画布创建 Prompt Chain 工作流，添加节点、连接节点、配置 Prompt 模板，保存草稿并发布为可运行版本。

**Why this priority**: 工作流编排是系统可扩展性的基础，但 MVP 阶段可先使用预置工作流验证核心生成链路，编排功能可后续完善。

**Independent Test**: 可通过设计者创建一个包含所有节点类型的工作流并成功发布来验证。

**Acceptance Scenarios**:

1. **Given** 设计者已登录, **When** 创建新工作流并添加节点连线, **Then** 画布正确显示流程结构
2. **Given** 工作流已配置完成, **When** 点击保存, **Then** 草稿被持久化且可再次打开编辑
3. **Given** 流程合法, **When** 点击发布, **Then** 工作流状态变为已发布且普通用户可见

---

### User Story 5 - 任务监控与结果回放 (Priority: P2)

用户可查看任务的运行状态、当前执行节点、各节点执行记录，并支持暂停/恢复任务和按时间线回放执行过程。

**Why this priority**: 监控和回放是系统可追溯性的核心体现，对于毕业设计演示和问题定位有重要价值，但不阻塞核心生成功能验证。

**Independent Test**: 可通过查看已完成任务的详情页，验证节点时间线、中间产物和执行状态的完整展示。

**Acceptance Scenarios**:

1. **Given** 任务正在运行, **When** 用户打开任务详情, **Then** 可看到当前节点、各节点状态和时间信息
2. **Given** 任务状态支持暂停, **When** 用户点击暂停, **Then** 任务状态变为已暂停且可稍后恢复
3. **Given** 任务已完成, **When** 用户查看回放, **Then** 可按执行顺序查看各节点的输入/输出/异常/干预记录

---

### User Story 6 - 管理员进行用户管理 (Priority: P3)

管理员可以新增用户、禁用/启用账号、为用户分配角色，查看异常任务和系统日志。

**Why this priority**: 用户管理是完整系统的必要组成部分，但 MVP 阶段可采用预置账号方式验证核心功能，管理功能可后续补充。

**Independent Test**: 可通过管理员创建新用户、修改角色、禁用账号的操作序列来验证。

**Acceptance Scenarios**:

1. **Given** 管理员已登录, **When** 新增用户并分配角色, **Then** 新用户可以对应角色登录系统
2. **Given** 存在活跃用户, **When** 管理员禁用该账号, **Then** 该用户无法登录

---

### Edge Cases

- 当工作流执行过程中 LLM 调用失败时，系统应记录错误并允许手动重试
- 当 JSON 结构化输出解析失败时，系统应记录异常并按配置的策略处理（重试/跳过/Gate）
- 当用户在 Gate 等待期间长时间未响应时，任务应保持等待状态直到明确处理
- 当工作流发布前校验不通过（如缺少开始/结束节点、存在孤立节点）时，系统应阻止发布并提示具体问题
- 当任务暂停后长时间未恢复时，系统应保持上下文持久化确保后续可恢复

## Requirements *(mandatory)*

### Functional Requirements

#### 身份认证与角色管理

- **FR-001**: 系统必须支持用户通过账号和密码登录，并建立有效会话
- **FR-002**: 系统必须在用户登录后识别其角色，并按角色加载相应菜单、页面和操作权限
- **FR-003**: 系统必须支持管理员新增、禁用、启用、查询用户，并为用户分配角色
- **FR-004**: 系统必须支持用户主动退出登录，并销毁当前会话

#### Prompt Chain 工作流可视化编排

- **FR-005**: 系统必须允许工作流设计者创建新的 Prompt Chain 工作流
- **FR-006**: 系统必须提供流程画布，支持拖拽节点、连接节点、删除节点、移动节点位置和配置节点属性
- **FR-007**: 系统必须至少支持以下节点类型：开始节点、输入节点、生成节点、解析节点、条件节点、Gate 节点、输出节点
- **FR-008**: 系统必须支持工作流草稿保存，保存后可再次打开继续编辑
- **FR-009**: 系统必须支持将草稿工作流发布为可运行版本
- **FR-010**: 系统必须在保存或发布前校验流程图合法性，包括是否存在开始节点、结束节点、孤立节点和缺失关键配置

#### 一键生成长文/脚本

- **FR-011**: 系统必须支持普通用户选择已发布工作流并填写输入参数，然后创建任务实例
- **FR-012**: 系统必须在生成流程开始阶段自动生成意图卡，对用户需求进行结构化归纳
- **FR-013**: 系统必须基于意图卡生成提纲，包括章节标题、结构层级和关键要点
- **FR-014**: 系统必须基于提纲生成长文或脚本正文
- **FR-015**: 系统必须在正文生成后执行自检修订，检查结构偏差、内容重复、表达不顺、约束未满足等问题
- **FR-016**: 系统必须保存意图卡、提纲、草稿、自检报告和终稿等中间产物
- **FR-017**: 系统必须支持对模型输出进行结构化 JSON 解析，并将解析结果供后续节点使用

#### 不确定点检测与人机门控

- **FR-018**: 系统必须在关键节点对任务输入和中间产物进行检测，识别缺信息、约束冲突、事实风险
- **FR-019**: 当检测到不确定点时，系统必须触发 Gate，将任务状态置为等待用户处理
- **FR-020**: 系统必须向用户提出 1-3 个关键问题，用于补齐缺失信息、消解冲突或降低事实风险
- **FR-021**: 用户提交回答后，系统必须将回答写入当前任务上下文，并从中断处继续执行后续节点
- **FR-022**: 系统必须提供待处理 Gate/审批任务列表和详情视图

#### 任务监控与结果回放

- **FR-023**: 系统必须维护任务状态，至少包括：待启动、运行中、等待确认、已暂停、已成功、已失败
- **FR-024**: 系统必须提供任务启动、暂停和恢复接口
- **FR-025**: 系统必须展示任务当前执行节点、各节点执行状态和时间信息
- **FR-026**: 系统必须支持按执行顺序回放任务全过程，包括节点输入、输出、中间产物、异常信息和用户干预记录
- **FR-027**: 系统必须支持流程图的顺序执行与条件分支执行
- **FR-028**: 系统必须在任务运行过程中持久化上下文状态，以支持任务恢复、Gate 继续执行和回放

### Non-Functional Requirements

- **NFR-001**: 系统必须采用 B/S 架构，体现前端、后端、模型调用和数据存储的明确分工
- **NFR-002**: 系统流程逻辑必须通过工作流配置与版本化管理实现可维护和可扩展
- **NFR-003**: 系统在节点失败、JSON 解析失败或 Gate 中断后，必须保证任务状态可恢复、上下文不丢失
- **NFR-004**: 系统必须完整记录任务执行过程，用于问题定位、结果回放和测试评测
- **NFR-005**: 系统必须确保用户身份受控、角色隔离有效、管理员功能不可越权访问
- **NFR-006**: 系统界面必须支持普通用户快速创建任务、查看结果和处理 Gate

### Key Entities

- **User (用户)**: 系统使用者，包含用户编号、用户名、密码摘要、角色编号、状态、创建时间
- **Role (角色)**: 权限分组，包含角色编号、角色名称、角色描述
- **Workflow (工作流)**: 流程定义的基本信息，包含工作流编号、名称、描述、创建者、当前版本、状态
- **WorkflowVersion (工作流版本)**: 工作流的特定版本，包含版本编号、工作流编号、版本号、流程定义JSON、发布状态、创建时间
- **Node (节点)**: 流程图中的节点，包含节点编号、版本编号、节点类型、节点名称、配置JSON、位置坐标
- **Edge (连线)**: 节点之间的连接，包含连线编号、版本编号、起点节点、终点节点、条件表达式
- **TaskRun (任务实例)**: 工作流的一次执行记录，包含任务编号、工作流版本、发起人、当前状态、当前节点、开始时间、结束时间
- **SessionState (会话状态)**: 任务执行上下文，包含状态编号、任务编号、上下文JSON、最近节点、恢复标记
- **Artifact (中间产物)**: 执行过程中的阶段性产物，包含产物编号、任务编号、产物类型、内容、来源节点、生成时间
- **GateRecord (Gate记录)**: 不确定点检测与处理记录，包含Gate编号、任务编号、触发原因、问题列表、用户回答、状态、处理时间
- **ExecutionLog (执行日志)**: 节点执行记录，包含日志编号、任务编号、节点编号、输入快照、输出快照、状态、耗时、错误信息

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户可以从输入主题到获得终稿的完整流程在合理时间内完成（长文生成类任务）
- **SC-002**: 系统检测到不确定点时，100% 触发 Gate 并生成 1-3 个相关问题
- **SC-003**: Gate 回答提交后，系统能够从中断点正确恢复执行，恢复失败率为 0%
- **SC-004**: 所有中间产物（意图卡、提纲、草稿、自检报告、终稿）均被持久化并可在任务详情页查看
- **SC-005**: 不同角色登录后，看到的菜单和可执行操作符合权限设计，越权访问率为 0%
- **SC-006**: 任务暂停后恢复时，上下文完整保留，状态一致性验证通过
- **SC-007**: 已完成任务的回放功能可展示完整执行过程，包括所有节点的输入/输出和用户干预记录
- **SC-008**: 工作流校验能够识别所有非法配置（缺少开始/结束节点、孤立节点等）并阻止发布

## Assumptions

- 系统使用现有后端技术栈（FastAPI + LangGraph + SQLAlchemy）和前端技术栈（Next.js + React + TypeScript）
- LLM 模型调用通过配置的 API（OpenAI/Anthropic）完成，不需要本地部署模型
- MVP 阶段优先验证核心生成链路闭环，高级工作流编排功能可逐步完善
- 用户角色暂定为三种：普通用户、工作流设计者、管理员
- 本系统是毕业设计项目，重点在于功能完整性和可演示性，而非大规模并发性能

## Constraints

- 重点应放在 Prompt Chain 工作流、Gate 机制、状态持久化和结果回放等主线能力上
- 系统应优先保证"核心闭环可跑通、关键功能可演示、文档材料完整"
- 页面元素用户可见文本默认使用中文
- 需与现有代码库中的 Artifact、NodeRun、WorkflowRun 等模型保持一致

## Dependencies

- 后端依赖 LangGraph 实现工作流执行引擎
- 前端可视化编辑器依赖 React Flow
- LLM 调用依赖 OpenAI/Anthropic API
- 数据持久化依赖 PostgreSQL
- 会话状态缓存依赖 Redis
